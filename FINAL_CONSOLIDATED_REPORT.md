## 2. Bugs found and exact fixes

B1 - lab-reports.js was entirely dead (critical).
Twelve lines of a previous edit had been pasted ABOVE the DOMContentLoaded
wrapper, referencing row, button and report at module scope. The browser threw
"ReferenceError: row is not defined", so NO lab-report page behaviour ever
registered. Fix: removed the stray fragment; the real handlers are untouched.

B2 - Lab report Delete button missing from the table.
The RBAC-gated delete button only existed inside that dead fragment, so rendered
rows had just View/Print. Fix: delete (and the new edit) button are emitted by
render() behind Permissions.can('lab-reports', 'delete' | 'edit').

B3 - Billing save handler could double-submit.
Only saveInvoiceBtn.disabled was set, which happens after the first await is
scheduled, so a fast second click could queue a second request. Fix: an explicit
invoiceSaveInFlight flag guards the whole function, plus a "Saving..." label and
disabled Cancel/X while in flight.

B4 - Billing errors surfaced raw error.message.
Fix: CareFlowAPI.describeError(error, action) maps every status (400, 401, 403,
404, 409, 413, 415, 422, 429, 500, 502, 503, 504) plus network/backend-unreachable
to a readable sentence, preferring the backend detail when present.

B5 - Billing "Overdue" status option was invalid.
Backend enum is Literal["Pending", "Paid"]; choosing Overdue produced a 422.
Fix: option removed (legacy values still render read-only in the table/stats).

B6 - Billing "Notes" textarea was a dead control.
No notes column exists on the Billing model, so typed text was silently
discarded. Fix: field removed, with a comment explaining what a real
implementation would require.

B7 - Sidebar clipped its own content. Root causes in section 9.

B8 - Mobile drawer had no Escape handler and three duplicated close paths.
Fix: a single openDrawer()/closeDrawer() pair used by the button, overlay,
nav-item clicks, Escape and the resize handler; aria-expanded maintained;
body.sidebar-open scroll lock is always removed, including on resize to desktop.

B9 - settings.html never loaded app.js.
It was the only sidebar page missing the shared script, so it had no
Escape-to-close drawer, no nav tooltips and no shared toggle behaviour. Detected
by the headless run (15 nav items with no title; Escape did not close at 768px).
Fix: app.js added before settings.js.

B10 - requirements.txt advertised Django as the "primary backend runtime".
Nothing under app/ imports Django; the only Django code is in _legacy_unused/.
Fix: the three Django pins removed and the header corrected.

## 3. Billing status - FIXED / VERIFIED STATICALLY

- Create and edit remain separate modes (editingBillId, setInvoiceModalMode).
- Create -> POST /billing. Edit -> PUT /billing/{id}. The router is generated by
  make_crud_router, which exposes POST "" and PUT "/{id}"; there is NO PATCH
  route anywhere in this backend, so PUT is correct.
- Editing always targets the existing id, so it cannot fall through to POST and
  duplicate an invoice.
- All supported fields load into the existing modal: patient, date, consultation,
  lab, medicine, status. Totals are recalculated client-side and again
  server-side on update.
- Line items: NOT IMPLEMENTED (out of scope). The Billing model has exactly three
  amount columns (consultation, lab, medicine) plus total. No line-item table
  exists, so no line-item editor was invented.
- Discount and tax: NOT IMPLEMENTED (out of scope). No such columns exist; no
  frontend-only fields were added.
- Payment status: FIXED. The backend does support it
  (BillingUpdate.status: Literal["Pending", "Paid"]). The select is validated
  against that enum, invalid values coerce to Pending, and the control is
  disabled with an explanatory tooltip for roles without billing.create /
  billing.edit. Audit logging already exists server-side
  (crud_factory._write_audit writes a row for every create and update), so no
  client-side audit call was added.
- Error handling covers 400/401/403/404/409/422/500 and network failure through
  describeError; a 404 during edit also resyncs the table.
- After a successful save the list is re-read from the server (loadBillingData())
  rather than patched locally.
- MANUAL TEST REQUIRED: live create/edit/delete/print against a running backend.

## Addendum — September 14, 2026

### Executive summary (this round)
Implemented all four requested billing/prescription features: itemized line items, discount & tax with server-side authoritative recalculation, an immutable void-and-reissue workflow for finalized bills, and a prescription instructions field. Notifications backend remained deferred per explicit instruction. Billing was promoted from the generic CRUD factory to its own dedicated router (`routers/billing.py`) since it now carries real business logic (calculation engine, void state machine) the generic factory was never meant to hold.

### Architecture note: Billing is no longer a "generic resource"
Every other simple resource (Doctors, Departments, Appointments, Lab Reports) still goes through `crud_factory.make_crud_router`. Billing does not, as of this session — it has its own file with its own create/update/void/delete logic, because those routes now do meaningfully more than "map a Pydantic model onto a SQLAlchemy row." This is a deliberate exception, not scope creep: the alternative (bolting item/discount/tax/void logic onto the generic factory) would have made the factor harder to reason about for every *other* resource that doesn't need any of it.

### Financial data integrity (the core ask across features 1, 2, and 4)
The unifying rule across the billing work this session: **the server is the only source of truth for money.** Concretely —
- Line item amounts, subtotal, discount amount, tax amount, and grand total are all recomputed server-side on every write, never taken from the client.
- A bill's totals cannot be corrupted by a stale or malicious frontend payload — even if the browser sends a wrong "total," it's discarded and recalculated.
- Once a bill is `Paid` or `Void`, it is provably immutable at the API layer (409 on PUT and DELETE) — the only path to changing a finalized bill's numbers is the void+reissue workflow, which preserves the original row forever and links it to whatever replaces it.

### Manual test checklist (additions)
- Create an invoice with 3+ line items, a percentage discount, and a flat tax; confirm the grand total matches hand calculation and persists correctly after a page refresh.
- Edit a Pending invoice's items and confirm totals recalculate; attempt to edit a Paid invoice and confirm it's blocked with a clear message.
- Void an invoice without entering a reason (should be blocked client-side) and with one (should succeed); confirm the reason and voider appear on the invoice view.
- Issue a corrected bill against a voided one; confirm both invoices show the cross-reference correctly in the UI.
- Create a prescription with instructions text, view it, print/export it, and confirm the text appears; edit an existing prescription's instructions and confirm the change is saved.

### Final readiness assessment (unchanged in kind, restated)
As with every prior round: everything above is backed by real source-level implementation and, where a live server wasn't available, by direct verification against a copy of the actual database using Python's stdlib `sqlite3` — genuinely stronger evidence than a read-through, but still not the same as a browser click-testing session. Nothing in this application should be declared production-ready without that pass; this report continues to say so rather than round up.
